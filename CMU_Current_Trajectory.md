# Central Memory Unit: Current Trajectory

Current direction: CMU should be a central, persistent memory layer for organization-level and team-level work where developers and autonomous agents operate together. It should remember not only raw events, but the useful patterns behind those events: similar situations, cause chains, accepted practices, avoidable mistakes, decision histories, and lessons that should improve future execution.

CMU memory should be situation-first, not document-first. The system should feel like an experienced teammate that recognizes the current scenario because it has seen similar situations before, then guides the agent and developer through the relevant pattern while codebase standards and team practices are learned naturally during the work.

The first core memory unit is a Situation Memory: a compact reusable record of a work scenario, not a transcript. It should capture the situation pattern, triggering signals, surrounding context, what was tried, what failed, what worked, why it worked, what practice it teaches, and when it should or should not be reused.

The second core memory unit is Practice Memory: a promoted memory that represents the currently trusted way to act in a defined scope. It should behave like a living precedent, not a fixed commandment. A Practice Memory should carry the practice, the conditions where it applies, the reasoning behind it, the supporting Situation Memories, known exceptions, and signals that would justify reconsidering it.

Practice Memory should act as a default path with a challenge protocol. If the current situation strongly matches the practice and there are no mismatch signals, CMU should quietly guide the agent to follow it. The challenge protocol should activate only when needed: changed constraints, architecture drift, security/performance concerns, failed application of the practice, strong new evidence, unusual risk, or a materially better path. A challenge should name the mismatch, expected benefit, risk, and rollback path, and its outcome should update the practice, create an exception, or strengthen the old precedent.

Memory should have stability levels. Candidate Memory is a rough draft from current work and can be discarded easily. Situation Memory is a validated reusable scenario and can still be refined by normal future evidence. Anchor Memory is costly-to-forget knowledge and should stay stable unless a serious challenge appears. Practice Memory is the accepted default way to act within a scope and should also stay stable unless the challenge protocol proves a better path or exception.

This means lower-level memory can evolve freely, but higher-level memory is dependable by default. Ordinary future encounters may confirm or use anchors and practices, but they should not casually weaken, reinterpret, or rewrite them. Only the deliberate challenge path should revise, split, retire, or upgrade stable memory.

Candidate Memory should be drafted only when work produces reusable situational intelligence, not merely because something notable happened. Draft triggers include repeated errors, successful fixes after failed attempts, surprising root causes, decisions with tradeoffs, accepted workarounds, unsafe paths avoided, new project conventions, hidden dependencies, ownership ambiguity resolved, test/deploy failures explained, architecture or contract changes, costly debugging sessions, challenges to Practice or Anchor memory, onboarding confusion, explicit "remember this" moments, reasonable-but-wrong agent assumptions, small local changes revealing larger system rules, undocumented tribal knowledge, performance or scaling surprises, security/privacy/compliance reasoning, dependency/version/tooling quirks, explained flaky tests, rollbacks or incidents, business/customer constraints affecting technical choices, files/modules becoming hotspots across unrelated tasks, prompt/instruction patterns affecting agent behavior, and human corrections that future agents should know.

The Candidate Memory filter should reject routine edits, obvious fixes, one-off noise, raw logs without a lesson, duplicates, and anything whose future cost of forgetting is low.

Memory promotion should use clear gates. Candidate -> Situation when the draft has a reusable scenario, evidence, outcome, scope, and at least one future-use reason. Situation -> Anchor when forgetting it has high future cost, such as production risk, data loss, security/privacy harm, expensive debugging, legal/business consequence, or strong architectural reasoning. Situation -> Practice when the approach is trusted enough to become the default path in a defined scope, with conditions, exceptions, evidence, and owner/team acceptance. Situation -> Exception when the lesson matters but applies only under specific conditions and should not become a general rule.

CMU should also support Anti-Pattern Memory and Question Memory. Anti-Pattern Memory is for tempting approaches that should be avoided, such as shortcuts that pass tests but create later instability or fixes that hide the root cause. Question Memory is for unresolved but important uncertainty where forgetting the question would be costly. This lets CMU preserve what worked, what must be avoided, and what must stay visible until resolved.

Memory scope should be multi-axis, not a single label. Every memory must answer where it is true before it can guide action. Scope dimensions include ownership scope (person/team/org authority), code scope (repo/module/file/API), workflow scope (debugging/refactor/deploy/onboarding/migration), environment scope (local/staging/prod/mobile/cloud), actor scope (human/new developer/agent/swarm), and time/version scope (when it became valid, when to review, and what versions it depends on).

Memory should start as narrow as possible and expand only when evidence shows broader applicability. This prevents false transfer, where a correct lesson in one context becomes dangerous in another. For example, a credential-rotation practice might apply only to a specific auth module, production-like environments, deployment agents, and versions after a lock-service change, rather than to all auth work.

Authority should be based on consequence, not bureaucracy. Low-consequence memories can be auto-created and refined by agents. Medium-consequence Situation or Exception memories can use lightweight owner review or passive confirmation. High-consequence Anchor and Practice memories need explicit authority because they guide future behavior and can create future cost if wrong.

The operating principle is graduated friction: ordinary learning should feel automatic, but friction should increase only when the memory's future cost, scope, or action-guiding power increases. To prevent bad memory from silently becoming trusted, stable memories need confidence, evidence links, owner scope, review/expiry signals, and the deliberate challenge path.

We discussed that a pure tree structure may be too rigid because one memory can belong to many contexts at once. The current best mental model is a graph-backed memory system with tree-like views: memories live as connected nodes, but humans and agents can view them as practical paths such as problem -> cause -> fix -> accepted practice.

Retrieval should likely be hybrid: embeddings for semantic similarity, graph relationships for structural relevance, and hard signals for grounding, such as same repo, module, error signature, workflow stage, team, decision owner, or time window. Embeddings alone may find things that sound similar but are not actually useful; graph and metadata help keep retrieval accurate.

CMU should surface memory on demand rather than dumping relevant memories into the active context window. It should sit outside the working context as a memory intelligence service. At the beginning of any meaningful task, the agent should run a lightweight CMU semantic preflight using the prompt, task area, likely files/modules, and actor type to check whether relevant memory exists before work begins. CMU should also be called when the agent reaches uncertainty, a risky area, a familiar-looking failure, a known module, a decision point, or a practice boundary. The response should be small and situation-shaped: matched situation, why it is relevant, recommended path, practice to follow, warnings, and when to challenge.

Embeddings should help locate the semantic area, but the memory tool should use graph links and hard signals to ground the result before anything reaches the context window. The goal is to make memory available exactly when needed while keeping the active context lean.

The fixed on-demand response shape is a CMU Action Note. It should be action-first, compact, and complete enough to guide the next move without becoming a memory dump. Fields: Recognized Situation, Why It Matches, Use This Path, Respect This Memory, Avoid This, Challenge Only If, Evidence, and Confidence. Normal notes should stay under about 180 tokens and high-risk notes under about 350 tokens.

The Use This Path section must include this operating rule when relevant as an escalation rule, not as the first memory check: "Don’t fight errors! Whenever you encounter the same error twice, research the web and find 3-5 possible ways to fix it. Then choose the most efficient solution and implement it." CMU should already have been checked through task-start preflight or a relevant trigger before the agent reaches this point.

The agent/developer experience should make CMU feel like a quiet senior teammate. When CMU shapes the work, the model response should include a brief natural line such as "Checked CMU and found a matching deploy-failure pattern, so I am going to verify the migration order before changing code." This line should mention the memory-backed lead and the immediate action, without exposing raw memory or creating a separate dashboard moment.

Practice/Anchor promotion should be handled through tiny review moments, not meetings. CMU can prepare a compact promotion card only when a memory is high-consequence or behavior-guiding, showing why it should become Anchor or Practice, its proposed scope, key evidence, and simple choices such as Approve, Narrow scope/Edit, or Keep as Situation. The developer should approve, narrow, or reject a prepared judgment rather than write memory from scratch.

Onboarding should use progressive apprenticeship, not a handbook dump. At the beginning, CMU should provide a task-bound Onboarding Seed generated from three inputs: actor, task, and area. The seed should answer only: where am I working, what must I not violate, what default path should I follow, what trap should I avoid, and when should I call CMU again.

The Onboarding Seed should stay extremely small. Normal target is about 120-220 tokens, with high-risk onboarding allowed up to about 350. Everything else should stay outside the context until triggered by semantic preflight, Action Notes, risky modules, repeated failures, practice boundaries, or explicit "why" requests.

The first product behavior should be the CMU Work Cycle: two quiet phases and two visible moments. Quiet phase one is task-start semantic preflight and retrieval before work, without dumping context. Visible moment one appears only if memory shaped the plan: the agent briefly says the CMU lead and immediate next action. Quiet phase two is Candidate Memory drafting during or after work without interrupting. Visible moment two appears only for high-consequence Practice/Anchor promotion review.

The Work Cycle is conditional, not a rigid sequence. If there is no relevant memory, CMU stays quiet. If work produces no reusable situational intelligence, no memory draft is needed. If promotion is not high-consequence or behavior-guiding, no review card appears. CMU should be always available, rarely loud, and visible only when it changes action or needs trust.

CMU needs a Call Trigger Layer so agents do not call memory constantly after the initial lightweight task-start preflight. Must-call triggers include: security, auth, payment, credentials, privacy, billing, data migration, deployment, CI, public API, database schema, shared contract, or permissions work; irreversible or hard-to-rollback changes; touching hotspot files or known-history modules; challenging a Practice or Anchor; architecture decisions; broad refactors; cross-team or unclear-ownership work; tests failing after an apparently correct fix; dependency/tool behavior uncertainty; repeated errors after the preflight path; stuck after reasonable local attempts; or any action with high future cost if wrong.

Should-call triggers include: entering an unfamiliar module, starting a large or multi-step task, onboarding a new agent or developer, touching legacy code, seeing a pattern that feels similar to past work, requirements ambiguity, or choosing between multiple plausible approaches.

Silent-skip applies when the task is small, local, low-risk, follows an obvious existing pattern, and has no repeated error, uncertainty, shared-contract impact, or future-cost risk. A CMU call should include goal, current situation, files/modules, error/signals, what was already tried, risk level, and the decision the agent needs help with.

For deciding where memory belongs, the strongest current idea is a Memory Gravity model. A candidate memory should naturally pull toward files, teams, product areas, failure patterns, accepted practices, onboarding gaps, decisions, or org-level principles based on shared evidence and future usefulness. Placement should evolve: memories can settle, merge, promote, demote, decay, or become anchors as reality keeps confirming or weakening them, while stable anchor and practice memory remain protected from casual change.

CMU should measure usefulness by whether memory changed the work for the better, not by vanity metrics like retrieval count. Strong usefulness signals include avoided repeated mistakes, reduced time/turns/tokens, prevented risky action, improved first-attempt success, choosing the right path sooner, smoother onboarding, fewer human corrections, better Practice discovery, and correctly triggered challenges.

CMU must also measure drag. If a memory is often ignored, causes confusion, adds unnecessary context, or does not change action, it should lose trust, be scoped down, or be reviewed. The test is whether memory makes the craft cleaner, faster, safer, and more consistent without making the worker manage extra burden.

The first practical usefulness signal is now Memory Use Receipts linked to Git checkpoints. When CMU surfaces memory through preflight, it records a use receipt. If the resulting work reaches a commit, the receipt can be linked to Git metadata: commit hash, message, changed files, and commit time. A commit is treated as strong positive evidence that memory-supported work reached an accepted checkpoint, but not as absolute proof that the memory itself was correct. Mixed commits, WIP/checkpoint commits, missing file context, low file overlap, delayed commits, and reverts lower confidence or should trigger review instead of blindly overwriting memory. Receipt signals may reorder actionable matches, but they must not make an otherwise quiet memory enter active context.

Future cost of forgetting should be estimated as Memory Liability: the debt or danger carried when knowledge is absent at the future point of work. Memory Liability should consider harm severity, recovery cost, rediscovery difficulty, affected scope, agent-misguidance risk, decision irreversibility, onboarding value, and practice-shaping value. This captures both rare disasters and slow invisible organizational decay.

A memory has high liability if forgetting it would cause expensive harm, repeated waste, wrong defaults, lost craft knowledge, security/privacy/business risk, or agent miscalibration. This liability sense should influence Candidate filtering, Anchor promotion, call triggers, authority friction, and Memory Gravity.

Recurrence is useful but should not dominate. CMU should rank memory primarily by the future cost of forgetting it. Rare but critical knowledge can be more important than frequent events if forgetting it could waste major time, break production, damage trust, corrupt data, or mislead agents. These rare high-consequence memories should have anchor weight even without many repetitions.

We also discussed that saving everything directly as memory would become noisy. A better product experience would feel seamless: people and agents work normally, CMU quietly captures activity, drafts possible memories, and only asks for attention when something is important enough to approve or confidence is low. Internally it may separate raw traces, distilled memories, and accepted practices, but the surface should stay calm.

Open thinking: how to prevent memory from becoming drag at scale.

Current strategic shift: the project should stop spending primary implementation cycles on tiny semantic-audit polish until the large structural skeleton of CMU is live. The recent small semantic evidence controls are useful, but they are refinement surfaces. The next phase must make every major conceptual subsystem work in at least a first complete form so CMU can produce evidence about its own assumptions.

The structural skeleton phase should prioritize large proof slices that connect multiple parts of the concept, even if the first version is simple. The goal is to answer, with actual outputs and data points: did memory change the work, did it reduce risk or drag, did a candidate become a reusable memory, did retrieval choose the right thing, did governance handle stable memory correctly, and did usefulness/drag analytics tell a believable story.

Large structural slices still needed:

1. Scenario and evaluation harness: repeatable scenarios that compare CMU behavior across task-start, retrieval, memory use, evidence, and review.
2. Core memory lifecycle: Candidate -> Situation -> Practice/Anchor/Exception, plus challenge, split, retire, strengthen, and scope refinement as one coherent loop.
3. Raw trace to distilled memory pipeline: a path from work activity or task output into candidate memory drafts, with noise rejection.
4. Memory Gravity: placement, settling, merging, demotion, decay, and scope pull based on evidence, liability, relationships, and future usefulness.
5. Full Hybrid Retrieval pipeline: candidate search -> hard grounding -> graph expansion -> semantic support -> ranking -> Action Note.
6. Practice/Anchor governance loop: following, challenging, strengthening, narrowing, splitting, retiring, and approving stable memory with explicit authority.
7. Usefulness and drag analytics: evidence that memory saved time, prevented mistakes, reduced risk, caused confusion, or failed to change action.
8. Full Work Cycle integration: trigger -> onboarding -> preflight -> action note or silence -> receipt -> after-work memory decision -> review.
9. Anti-Pattern workflow: first-class creation, retrieval, evidence, and review for tempting paths to avoid.
10. Question workflow: first-class creation, surfacing, tracking, and resolution of important unresolved uncertainty.
11. Graph memory view: inspectable situation -> cause -> fix -> practice -> exception paths rather than flat records only.
12. Agent integration boundary: a realistic tool-call/API shape beyond manual CLI use.
13. Team and authority model: ownership, approval, consequence-based permissions, review expiry, and multi-actor governance.
14. Memory quality and decay model: weakening, demotion, expiry, review, and removal when memories stop helping.
15. Import/export and portability layer: a clean boundary for moving memory data beyond one local JSON shape later.

Current automatic evidence-loop slice now completed: `cmu evidence-monitor` can inspect recent Git checkpoints, reuse CMU's auto-link scoring, and apply only clean high-confidence committed receipt links with `--apply`. Risky evidence such as WIP/checkpoint commits, reverted commits, mixed commits, delayed commits, no-overlap commits, low-confidence matches, and ambiguous matches remains review-only. This is the first cautious move from command-driven evidence linking toward automatic usefulness evidence.

Current governance/review UX slice now completed: `cmu review-queue` turns scattered promotion, stable authority, team-scope coverage, active challenge, strengthen, governance review, and decay signals into compact read-only approval cards with exact existing follow-up commands. This gives CMU a clearer human review moment without weakening authority gates or applying stable-memory changes silently.

Current lifecycle automation slice now completed: `cmu lifecycle-apply --candidate-ready` provides the first controlled lifecycle mutation path. It previews by default and can promote only gate-passing Candidate memories to Situation with `--apply`, while leaving blocked Candidates unchanged and keeping Practice/Anchor promotion under explicit authority review.

Current local team-scope directory slice now completed: `cmu team-scope-add`, `cmu team-scope`, and `cmu review-queue` provide the first explicit repo/team boundary map plus human review moment. CMU can now record local ownership boundaries with code/workflow/environment scope, authority role, and consequence, report whether active memories cover those boundaries, and surface uncovered boundaries as review cards. This is useful in exactly the planned sense: it makes false transfer across repos and teams visible before broader multi-repo or organization-level authority exists, and it rejects environment-only overlap as insufficient coverage.

Current portable compatibility fixture slice now completed: `cmu portable-compat` gives portable memory bundles a saved-fixture regression gate. Current valid bundles must keep validating, intentionally invalid bundles must keep failing, and future-schema bundles must fail safely as unsupported until an explicit migration path exists. This matters because organizational memory should be movable without becoming silently corrupt or silently over-trusted across schema changes.

Current review reminder slice now completed: `cmu review-reminders` turns expired or due-soon stable-memory authority reviews and open high-priority approval cards into a compact read-only reminder list. This keeps the intended governance feel: CMU can tap the shoulder when trust needs renewal without turning stable-memory review into automatic mutation or ceremony.

Current fixture repository slice now completed: `cmu fixture-repo-create --kind checkout-release` creates a real repo-shaped scenario fixture with source files, tests, scoped Practice memory, and a saved strict scenario. This is a practical step toward serious evaluation because CMU behavior can now be checked against concrete host-path repositories rather than only abstract prompts.

Future industry-patterns to borrow after the main engine is dependable:

- From Mem0-style systems, borrow fast SDK ergonomics, simple setup, clear memory APIs, and the feeling that adding memory to an agent takes minutes rather than a deep platform migration.
- From Zep/Graphiti-style systems, borrow temporal knowledge graph discipline: first-class entities, relationships, event time, fact invalidation, history-aware reasoning, and serious graph traversal beyond flat retrieval.
- From Letta/MemGPT-style systems, borrow tiered memory design and agent-editable working memory, but keep CMU's authority gates so stable Practice and Anchor memory cannot be casually rewritten by an agent.
- From LangMem/LangGraph-style systems, borrow background consolidation, reflection-style memory extraction, and smooth integration with existing agent runtimes instead of requiring developers to manually call CMU forever.
- From Supermemory/MCP-style systems, borrow broad tool access through MCP so CMU can become available across coding agents, chat agents, IDEs, and workflow tools without custom integration for every surface.
- From mature developer platforms, borrow a boring installation and demo path: `cmu-mcp`, a small SDK, a hosted or local quickstart, and a five-minute proof where CMU checks memory before work, prevents a known mistake, links the resulting commit, and shows usefulness evidence.
- From production memory systems generally, borrow evaluation discipline: retrieval precision/recall tests, latency budgets, privacy controls, import/export paths, migration/versioning support, and benchmarks that compare CMU against generic vector memory and graph memory baselines.
- Keep these as later adoption and hardening patterns. They should not displace the current priority: proving CMU's own main engine around situation recognition, Memory Liability, scoped authority, Practice/Anchor governance, challenge paths, and usefulness/drag evidence.
